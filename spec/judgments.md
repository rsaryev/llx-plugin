# Judgments

Behaviour the kit decides where the official docs and types are silent (docs/SPEC.md). Each entry
names the code that holds it and why. A judgment is never counted as compatibility.

| Where                         | Judgment                                                                                          | Why                                                                                       |
| ----------------------------- | ------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| `src/format/names.ts`         | The wording of the "not kebab-case" and "may not contain …" messages                              | The docs name the rules but quote no message for them                                     |
| `src/format/manifest.ts`      | The wording of "Unknown field", type-mismatch and missing-metadata messages                       | The docs say these are reported, not their text                                           |
| `src/format/paths.ts`         | The wording of "must start with ./" and "must be .md files"                                       | The docs state the rule; only the `..` message is quoted, and that one is used verbatim   |
| `src/format/manifest-schema.ts` | `author`, `dependencies` objects and `commands` entries are not strict (unknown keys dropped)   | "Unrecognized fields" lists the strict objects; these are not among them                  |
| `src/format/frontmatter.ts` | A block with no closing `---` is not frontmatter (the whole file is body); the closing marker is the first later line that is only `---`; a leading byte order mark is ignored; an empty block is present with no fields | skills.md fixes only the opening line and the unparseable-YAML case |
| `src/format/frontmatter.ts` | YAML is read with the 1.2 core schema (`yes`/`on` stay strings; a duplicate key does not parse) | The docs list the flag spellings but not the parser |
| `src/format/frontmatter-values.ts` | How a bad value is reported (the wording of each reason), that a number or boolean is read as text, that an enum matches exactly with no case folding, and that blank text is absent | The docs name the accepted spellings, not what happens to the rest |
| `src/format/frontmatter.ts` | A block that parses to a list or a single value is `not-a-table`: the file loads with no fields, like unparseable YAML; `line` and `column` count from the opening `---` as line 1 | The docs name only the unparseable case and send users to the parse error, not where it is |
| `src/format/frontmatter-values.ts` | `readInteger` takes a YAML number or a string of digits that is a safe integer, and reports a value outside `min`/`max` as dropped; `readList` has no default separator mode, each field picks one | The docs name the numeric limits and the list spellings per field, not how a bad one is handled |
| `src/rules/parse.ts` | The wording of every rule issue except the two quoted ones (the malformed-rule message and the matches-no-tool warning): the mcp__ parentheses (settings files only), tool-glob specifier, unanchored allow glob and primary-field messages | The docs name the conditions and link error pages but quote no text for these |
| `src/rules/parse.ts` | The severity of a skipped rule is `error` (malformed, mcp__ with parentheses in a settings file, a glob with a specifier); an ignored or never-matching rule (primary-field parameter rule, unanchored allow glob) is a `warning` | permissions.md says "ignores it and emits a startup warning" for the primary field only; the rest only says "skipped" |
| `src/rules/parse.ts` | Surrounding whitespace of a settings entry is trimmed; `Tool()` reads as the bare tool name; a tool-name glob (`*` in the tool name) with a specifier is skipped | The docs give the grammar `Tool` or `Tool(content)` and the bare `Bash(*)`, nothing on blanks, empty parentheses or a glob with a specifier |
| `src/rules/specifier-formats.ts` | `Tool(*)` reads as the bare tool name for the command format (Bash and Monitor), and for no other tool | Only `Bash(*)` is documented as equivalent to `Bash`; Monitor shares Bash's rule format in the tools-reference table |
| `src/rules/param.ts`, `src/rules/specifier-formats.ts` | How `name:value` is told from a command, path or skill pattern: a parameter name is an identifier of two letters or more or a `-x` flag; for Bash, Monitor and PowerShell `name:value` is a parameter rule only when `name` is a field of the tool's input, and `name:*` stays the `:*` suffix; `domain:` is a domain pattern for WebFetch | permissions.md fixes the `Tool(param:value)` form and the `:*` suffix but not how they are told apart; `git:* push` and a Windows `C:\x` path must stay patterns |
| `src/rules/param.ts` | A number or boolean input compares as its text (`run_in_background:true` matches the boolean `true`, `timeout:5000` the number 5000); an object, array, null or missing field never matches; only own fields of the input count | The docs say "the literal input Claude sends" and "scalar parameter", not how a non-string scalar is written; `Bash(run_in_background:true)` is the documented example |
| `src/rules/param.ts` | Whitespace is trimmed around the colon and at both ends of the name and the value | The docs say "Whitespace around the colon is ignored", not about the ends |
| `src/rules/specifier-formats.ts`, `src/rules/evaluate.ts` | A text or domain specifier on a tool the "Rule format" table does not list goes to the `bare` matcher; until its sub-package replaces it the kit's matcher of every format fails closed: an allow rule matches nothing, a deny or ask rule matches every call of its tool | The table says unlisted tools "accept only the bare tool name", not what a specifier on one does; a matcher that skips a deny rule would let the call through unchecked, so the placeholder errs toward denying and asking |
| `src/rules/tool-pattern.ts` | A tool-name glob knows only `*` (any characters, case-sensitive, whole name); `?` and `[...]` are literal | permissions.md names `*` in every example of "Tool name wildcards" and says nothing of other glob characters |
| `src/rules/issues.ts` | The matches-no-tool warning uses the longer stderr form quoted in errors.md, with the rule as it was written (`PermissionRule.text`, trimmed), at path `permissions.<behavior>` | errors.md quotes both forms (the startup row and the stderr line); the kit has one line to give |
| `src/protocol/tool-names.ts` | `DOCUMENTED_TOOLS` holds the 46 names of the tools-reference table (the design said 53): the 45 that are not removed plus the nine SDK-only names are the SDK's 54 `BUILTIN_TOOL_NAMES` | The table is the source; the count in the design was wrong |
| `src/rules/sources.ts` | The policy an embedding host passes (`managedSettings`) is `embedder-managed`, read as settings content: an `mcp__` rule with parentheses is skipped there like in a file; the command line and the session are the only sources that read it as a parameter rule | permissions.md says the skip is for "a settings file" and names `--disallowedTools` as the way around it; it does not place the SDK option |
| `src/rules/parse.ts` | An allow rule `mcp__server__tool(x:y)` from the command line or the session parses as a text specifier and approves nothing | The docs name only "a deny rule with `--disallowedTools`" for an MCP parameter, and an allow rule never matches by parameter |
| `src/rules/param.ts`, `src/rules/types.ts` | The names a skill goes by come from the host (`PreparedCall.skillNames`); only a deny rule matches `Skill(skill:<name>)` under any of them, an ask rule matches the literal input | permissions.md says "deny rule" and skills.md owns the names (alias, display name, nested and synced forms); the kit holds no skill catalog |
| `src/rules/param.ts` | A `Monitor(command:x)` rule is an ordinary parameter rule: the primary fields are the per-tool list of permissions.md, which names Bash and PowerShell but not Monitor | The docs are silent on Monitor; the kit does not extend a list the docs give |
| `src/rules/param.ts`, `src/rules/specifier-formats.ts` | PowerShell has no SDK input type, so its primary field is `command` as the docs say and its parameter names are Bash's input fields | The SDK types `BashInput` and `MonitorInput` only; hooks.md gives PowerShell's `tool_input` no field list |
| `src/rules/param.ts` | A rule that names two parameters (`Agent(model:opus, isolation:worktree)`) reads the text after the first colon as one value, so it matches neither call | The docs say to write two rules "rather than combining them", not what a combined rule does |
