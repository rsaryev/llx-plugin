# Judgments

Behaviour the kit decides where the official docs and types are silent (docs/SPEC.md). Each entry
names the code that holds it and why. A judgment is never counted as compatibility.

| Where                         | Judgment                                                                                          | Why                                                                                       |
| ----------------------------- | ------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| `src/format/names.ts`         | The wording of the "not kebab-case" and "may not contain …" messages                              | The docs name the rules but quote no message for them                                     |
| `src/format/manifest.ts`      | The wording of "Unknown field", type-mismatch and missing-metadata messages                       | The docs say these are reported, not their text                                           |
| `src/format/paths.ts`         | The wording of "must start with ./" and "must be .md files"                                       | The docs state the rule; only the `..` message is quoted, and that one is used verbatim   |
| `src/format/manifest-schema.ts` | `author`, `dependencies` objects and `commands` entries are not strict (unknown keys dropped)   | "Unrecognized fields" lists the strict objects; these are not among them                  |
| `src/format/frontmatter.ts` | A block with no closing `---` is not frontmatter (the whole file is body); the closing marker is the first later line that is only `---`; a leading byte order mark is ignored; an empty block is present with no fields | skills.md fixes only the opening line and the unparseable-YAML case |
| `src/format/frontmatter.ts` | YAML is read with the 1.2 core schema (`yes`/`on` stay strings; a duplicate key does not parse) | The docs list the flag spellings but not the parser |
| `src/format/frontmatter-values.ts` | How a bad value is reported (the wording of each reason), that a number or boolean is read as text, that an enum matches exactly with no case folding, and that blank text is absent | The docs name the accepted spellings, not what happens to the rest |
| `src/format/frontmatter.ts` | A block that parses to a list or a single value is `not-a-table`: the file loads with no fields, like unparseable YAML; `line` and `column` count from the opening `---` as line 1 | The docs name only the unparseable case and send users to the parse error, not where it is |
| `src/format/frontmatter-values.ts` | `readInteger` takes a YAML number or a string of digits that is a safe integer, and reports a value outside `min`/`max` as dropped; `readList` has no default separator mode, each field picks one | The docs name the numeric limits and the list spellings per field, not how a bad one is handled |
| `src/rules/parse.ts` | The wording of every rule issue except the two quoted ones (the malformed-rule message and the matches-no-tool warning): the mcp__ parentheses (settings files only), tool-glob specifier, unanchored allow glob and primary-field messages | The docs name the conditions and link error pages but quote no text for these |
| `src/rules/parse.ts` | The severity of a skipped rule is `error` (malformed, mcp__ with parentheses in a settings file, a glob with a specifier); an ignored or never-matching rule (primary-field parameter rule, unanchored allow glob) is a `warning` | permissions.md says "ignores it and emits a startup warning" for the primary field only; the rest only says "skipped" |
| `src/rules/parse.ts` | Surrounding whitespace of a settings entry is trimmed; `Tool()` reads as the bare tool name; a tool-name glob (`*` in the tool name) with a specifier is skipped | The docs give the grammar `Tool` or `Tool(content)` and the bare `Bash(*)`, nothing on blanks, empty parentheses or a glob with a specifier |
| `src/rules/specifier-formats.ts` | `Tool(*)` reads as the bare tool name for the command format (Bash and Monitor), and for no other tool | Only `Bash(*)` is documented as equivalent to `Bash`; Monitor shares Bash's rule format in the tools-reference table |
| `src/rules/param.ts`, `src/rules/specifier-formats.ts` | How `name:value` is told from a command, path or skill pattern: a parameter name is an identifier of two letters or more or a `-x` flag; for Bash, Monitor and PowerShell `name:value` is a parameter rule only when `name` is a field of the tool's input, and `name:*` stays the `:*` suffix; `domain:` is a domain pattern for WebFetch | permissions.md fixes the `Tool(param:value)` form and the `:*` suffix but not how they are told apart; `git:* push` and a Windows `C:\x` path must stay patterns |
| `src/rules/param.ts` | A number or boolean input compares as its text (`run_in_background:true` matches the boolean `true`, `timeout:5000` the number 5000); an object, array, null or missing field never matches; only own fields of the input count | The docs say "the literal input Claude sends" and "scalar parameter", not how a non-string scalar is written; `Bash(run_in_background:true)` is the documented example |
| `src/rules/param.ts` | Whitespace is trimmed around the colon and at both ends of the name and the value | The docs say "Whitespace around the colon is ignored", not about the ends |
| `src/rules/specifier-formats.ts`, `src/rules/evaluate.ts` | A text or domain specifier on a tool the "Rule format" table does not list goes to the `bare` matcher; until its sub-package replaces it the kit's matcher of every format fails closed: an allow rule matches nothing, a deny or ask rule matches every call of its tool | The table says unlisted tools "accept only the bare tool name", not what a specifier on one does; a matcher that skips a deny rule would let the call through unchecked, so the placeholder errs toward denying and asking |
| `src/rules/tool-pattern.ts` | A tool-name glob knows only `*` (any characters, case-sensitive, whole name); `?` and `[...]` are literal | permissions.md names `*` in every example of "Tool name wildcards" and says nothing of other glob characters |
| `src/rules/issues.ts` | The matches-no-tool warning uses the longer stderr form quoted in errors.md, with the rule as it was written (`PermissionRule.text`, trimmed), at path `permissions.<behavior>` | errors.md quotes both forms (the startup row and the stderr line); the kit has one line to give |
| `src/protocol/tool-names.ts` | `DOCUMENTED_TOOLS` holds the 46 names of the tools-reference table (the design said 53): the 45 that are not removed plus the nine SDK-only names are the SDK's 54 `BUILTIN_TOOL_NAMES` | The table is the source; the count in the design was wrong |
| `src/rules/sources.ts` | The policy an embedding host passes (`managedSettings`) is `embedder-managed`, read as settings content: an `mcp__` rule with parentheses is skipped there like in a file; the command line and the session are the only sources that read it as a parameter rule | permissions.md says the skip is for "a settings file" and names `--disallowedTools` as the way around it; it does not place the SDK option |
| `src/rules/parse.ts` | An allow rule `mcp__server__tool(x:y)` from the command line or the session parses as a text specifier and approves nothing | The docs name only "a deny rule with `--disallowedTools`" for an MCP parameter, and an allow rule never matches by parameter |
| `src/rules/param.ts`, `src/rules/types.ts` | The names a skill goes by come from the host (`PreparedCall.skillNames`); only a deny rule matches `Skill(skill:<name>)` under any of them, an ask rule matches the literal input | permissions.md says "deny rule" and skills.md owns the names (alias, display name, nested and synced forms); the kit holds no skill catalog |
| `src/rules/param.ts` | A `Monitor(command:x)` rule is an ordinary parameter rule: the primary fields are the per-tool list of permissions.md, which names Bash and PowerShell but not Monitor | The docs are silent on Monitor; the kit does not extend a list the docs give |
| `src/rules/param.ts`, `src/rules/specifier-formats.ts` | PowerShell has no SDK input type, so its primary field is `command` as the docs say and its parameter names are Bash's input fields | The SDK types `BashInput` and `MonitorInput` only; hooks.md gives PowerShell's `tool_input` no field list |
| `src/rules/param.ts` | A rule that names two parameters (`Agent(model:opus, isolation:worktree)`) reads the text after the first colon as one value, so it matches neither call | The docs say to write two rules "rather than combining them", not what a combined rule does |
| `src/rules/bash/split.ts`, `src/rules/bash/keywords.ts` | The command splitter is the kit's own quote-aware scanner: a command is split at the documented separators outside single and double quotes and after a backslash; a `&` that belongs to a redirect (`2>&1`, `<&3`, `&>`) is not a separator; commands inside `$()`, backticks, `( )`, process substitution and, for PowerShell, `{ }` are subcommands too; `${ }` and `$(( ))` are text except for what is substituted inside; `do`, `then`, `else`, `if`, `elif`, `while`, `until`, `!`, `{`, `case x in` and a `a)` label are keywords before a command, `done`, `fi`, `esac`, `}` and `for`/`select` headers are not commands; comments are not recognised; a here-document with a quoted delimiter has an inert body, one with an unquoted delimiter is read as commands, and the `<<` of a here-string (`<<< 'x'`) opens no here-document; nesting past 32 levels is unparseable | permissions.md names the separators and the nested forms but not an algorithm; every choice errs toward more subcommands, which only prompts more for an allow rule and denies more for a deny rule |
| `src/rules/bash/split.ts`, `src/rules/bash/shell.ts` | The only unparseable commands are those with nothing after `&&` or `||`, an unclosed quote, substitution or bracket, and nesting past the depth limit; the 10,000-character limit is a read-only-set rule and is not applied to rule matching. An unparseable command never matches an allow rule (not even by its whole text); a deny or ask rule tries the subcommands found so far and the whole text | permissions.md gives `npm test &&` as the example and says the command is not split "for allow-rule matching"; it says nothing of deny and ask, which must not let a call through unchecked |
| `src/rules/bash/wrappers.ts` | A rule is tried against a subcommand as written and after each wrapper or assignment is stripped in turn, not only the fully stripped form; the options of each wrapper (`timeout -s SIG -k DUR DURATION`, `nice -n N` or `-N`, `stdbuf -oL`, `time -p`, `command -p`) are the kit's reading of their manuals, `command -v` and `-V` are not stripped, and a wrapper with no command after it is left alone | The docs say "also matches" and "strips a fixed set" but not the options each takes, and a rule that names the wrapper (`Bash(timeout *)`) must keep working |
| `src/rules/bash/wrappers.ts` | The known-safe environment variables are `NODE_ENV`, `LANG` and `NO_COLOR`, plus `MatchContext.safeEnvVars`; a leading assignment is `NAME=value` with the name an identifier | The docs say "certain known-safe environment variables" and name those three as examples |
| `src/rules/bash/exec-wrappers.ts` | Besides `-exec`, `-delete`, `-rm`, `-fprint` and `-files0-from`, `find` with `-execdir`, `-ok`, `-okdir`, `-fprint0`, `-fprintf` or `-fls` needs an exact rule; wrappers and assignments before the command are seen through; the guard applies to allow rules that hold a `*` (or the `:*` suffix) and never to a deny or ask rule | The docs say "an action that runs commands, deletes files, or writes files, such as" four names; the others are find's actions of the same classes |
| `src/rules/bash/powershell.ts`, `src/rules/bash/dialect.ts` | PowerShell commands are split by the same scanner with `&&`, `||`, `;`, `|` and newline as separators, the backtick as the escape character, `{ }` as a block that holds commands, and `&` as the call operator; the alias table is `gci`, `ls` and `dir` for `Get-ChildItem`, applied to the first word of each subcommand and of the rule, so a rule written with an alias matches the cmdlet and the other aliases; no wrappers or assignments are stripped | The docs describe a PowerShell AST the kit does not have and name three aliases; resolving both sides keeps `PowerShell(ls *)` and `PowerShell(Get-ChildItem *)` the same rule |
| `src/rules/bash/if-eval.ts` | `evaluateIf` reads the `if` text as a deny rule from the command line (any subcommand matches; `name:value` is a parameter rule), runs the hook for a rule it cannot read (with the rule's issues), for a command with no string `command`, and for an unparseable command; "specifies more than the command name" is a pattern whose text before the trailing ` *` has more than one word, and `$VAR` is `$` followed by a letter, `_` or `{`, found by the splitter's quote-aware scan (outside single quotes, not escaped, an apostrophe inside double quotes opens nothing); a `Bash(...)` rule also answers a Monitor call, a `Monitor(...)` rule never a Bash call (hooks.md, "Match Monitor commands"); an issue about the `if` text is reported at path `hooks.if` (the hooks engine may refine it) with a note that the filter does not apply and the hook runs for every call, the rule being read as a deny rule only to reuse the permission-rule parser | hooks.md says the filter is best effort and runs the hook when it "can't determine" the commands, and gives one example of a pattern that says more than the name |
| `src/rules/bash/wildcard-warning.ts` | The wildcard-before-subcommand warning applies to a `Bash` allow rule whose first `*` word follows only options after the program and is followed by a literal word (`git * main`, `git -C * status *`), never to `Bash(git log * main)`, a rule with a wildcard program, or a deny or ask rule; its text is the stderr form of errors.md without the program-specific sentence and the settings path | errors.md describes "a `*` before a later word that determines which command it is" without a rule for where the subcommand is, and its quoted text names the settings file, which the kit does not know |
| `src/rules/path/depth.ts` | "A relative pattern with a single directory segment" is a pattern with one literal directory name, one slash and something below it (`src/**`, `src/*.ts`, `src/index.ts`), including a `**` between the directory and the rest (`src/**/*.ts`); a deny or ask rule of that shape matches at any depth under the cwd, an allow rule only at the anchor. A pattern starting with `/`, `**` or `!`, or holding two directories, is another shape | The docs show `src/**` and `secrets/**` only; widening the other one-directory shapes errs towards blocking for deny and ask and changes nothing for allow |
| `src/rules/path/anchor.ts` | `./path` is read as `path`: the same anchor, but a bare name or glob with no slash (`./.env`, `./*.env`) is anchored at the cwd and does not match at any depth, as `Read(.env)` does; a `../` prefix moves the anchor to the parent directory of the cwd, once per `../` | The docs list `path` and `./path` as one pattern type, say `Read(./.env)` matches "the `.env` file in the current directory" and `Read(.env)` any `.env` at or under it, and say nothing of `../` |
| `src/rules/path/anchor.ts` | A `/path` rule from the managed tiers (`managed`, `embedder-managed`) anchors at the primary working directory, like CLI and session rules; a `--settings` file given relatively resolves against the primary working directory | The source table lists five sources and no managed tier |
| `src/rules/path/glob.ts` | Matching is case-sensitive for a POSIX host and case-insensitive for a Windows host (`PathContext.platform`); a pattern is usable unless it is blank (`./` alone), a `#` comment or `/` alone, and an unusable deny or ask pattern guards the one path it spells (anchor root plus the text; `/` alone spells the anchor itself, not the filesystem root); `..hidden` is a name, only `..` and `../x` are parent climbs | The docs call an unusable pattern one that is "not usable as a gitignore pattern" without a list, and are silent on case |
| `src/rules/path/glob.ts`, `src/rules/path/tools.ts` | A Grep or Glob call is a search of a directory: a pattern covers it when it covers the path itself or the files below it (`Read(docs/**)` covers a search of `docs`), and a search with no `path` searches the cwd, which no pattern under the cwd covers | permissions.md says an ask rule prompts "when Claude calls Grep or Glob on a matching path, but not when a search of a working directory above it returns matching files"; how a directory matches `docs/**` is not stated, gitignore itself does not match `docs` |
| `src/rules/path/file-rules.ts` | `Write(*)`, `Glob(*)`, `Grep(*)`, `NotebookEdit(*)` and the legacy `MultiEdit(*)` cover every use of the tool; any other path on these five never matches. MultiEdit carries its path in `file_path` like Edit (the SDK has no type for it): an Edit rule covers it for allow, ask and deny, and a Read deny rule blocks it like Edit. An LSP path rule is read as unreadable: a deny or ask rule covers every LSP call, an allow rule none; a Read deny or ask rule reaches LSP the same way (no `!` carve-out reopens it), a Read allow rule does not. A Read ask rule does not reach Edit and Write, and an Edit deny or ask rule does not reach Read | The docs say these rules are accepted but never match "a path other than `*`" and to write the bare name for every use; MultiEdit is listed as a legacy tool "Edit rules cover" but has no input type; LSP is in the Read row of the format table ("Read, Grep, Glob, LSP") with no path field named, so the kit errs towards blocking; the Read-deny and Edit-allow implications are stated for those behaviours only |
| `src/rules/path/negation.ts` | A `!` rule carves out of the rules listed before it in the same list: the same source (a `--settings` file by its path), behaviour and tool name; only deny and ask rules carve, an allow rule starting with `!` approves nothing, and a `!` rule never covers a path itself | The docs describe "one settings file's `deny` list" and the same-source limit; the ask list and the tool boundary follow from "the rules listed before it" |
| `src/ports/path-resolver.ts`, `src/rules/path/symlink.ts` | `PathResolver` takes and returns the kit's POSIX form (on Windows `/c/...`); `prepareCall` resolves the nearest existing parent of a path that does not exist and appends the rest, records the target in `resolvedPaths` only when it differs, and returns a resolver's `PortFailure` instead of a call, so the host refuses the operation; a rule's real directory comes from `resolveRuleDirectories` (posix hosts, deny and ask rules written with `//`, `~/` or `/`, the directory before the first wildcard) | The docs say what is checked and that an unresolvable path is refused, not how a host resolves it or how a rule's directory is found |
| `src/rules/path/cd.ts` | `Cd(<pattern>)` compiles to a whole-path expression: `*` is within one segment, `**` between segments is zero or more segments, a trailing `/**` also matches its root; a relative pattern is under the cwd | The table gives four examples; `**` in the middle and the empty match follow the same reading |
| `src/rules/path/network.ts` | `readsNetworkPath` covers Read, Grep and Glob (the tools that read files), by the named path or any resolved one; a Windows path is a network path when it starts with `\\` or `//`, a POSIX path when it is `/net` or under it | The docs name "Read, Grep, and Glob" as examples ("such as") and one UNC and one `/net` spelling |
